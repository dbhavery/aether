## 1. What Phase 4 actually is

Per the roadmap, Phase 4 = "Tools and autonomy." Seven items:
1. Browser workflow capability (scoped)
2. File workflow capability (scoped)
3. Safer automation patterns
4. Action approval framework (policy engine maturity)
5. Audit / replay surfaces
6. Model escalation logic (router maturity)
7. Red-team test suite v1

T1.3 covers items 1 + 2 — the two new **capability-bearing** tool surfaces — plus the L5 enforcement work needed to gate them. Items 3–6 mature *existing* subsystems and are not new packages. Item 7 is already in flight (T2.2 red-team harness shipped 2026-04-29).

## 2. New surfaces this proposes

### 2.1 `packages/l5-browser/` (new crate)
- L5-gated browser automation primitives: `BrowserOpen`, `BrowserNavigate`, `BrowserClick`, `BrowserFillForm`, `BrowserExtract`, `BrowserScreenshot`.
- Each primitive is a `Capability` per `packages/l5-policy::Capability`. Approval mode follows the autonomy preset (Observer = Deny, Assistant = Ask, Operator = Auto for navigation + read, Ask for write/submit/login).
- Wraps Playwright via subprocess (cross-platform, mature, headless-safe). Tauri command surface mirrors the existing capability-gated commands.
- **Scope ceiling:** read + click + fill + extract. **No** credential persistence, **no** off-list navigation in Operator mode (must drop to Ask), **no** auto-submit on financial / auth / purchase pages (hard-blocked unless Power User + per-action confirm — Critical risk class per planning/12 §"Risk classes").

### 2.2 `packages/l5-files/` (new crate)
- L5-gated file workflow primitives: `FilesRead`, `FilesCreate` (already exist), plus `FilesEdit`, `FilesDelete`, `FilesMove`, `FilesArchive`, `FilesGrep`.
- Each is a `Capability`. Operator preset gets `FilesRead` + `FilesCreate` + `FilesEdit` + `FilesGrep` Auto inside approved scopes; `FilesDelete` + `FilesMove` stay Ask.
- Approved scope = directory tree the user explicitly granted via the existing approval framework. Outside-scope writes are Deny in all presets (Observer through Operator); Power User can grant on a per-session basis.

### 2.3 Action approval framework upgrades (in existing `l5-policy`)
- Per planning/12 §"Approval patterns": expand from "Auto / Ask / Deny" trio to also support **"Ask once per session / task"** and **"Draft only"**.
- New `ApprovalScope` field on `MediationDecision` events. Backwards-compatible: existing call sites default to per-action.

### 2.4 Audit replay surfaces
- A `tools/audit-replay/` CLI that takes an `aether_audit.db` slice and replays the action chain into a transcript. Read-only. Useful for incident review, red-team scenarios, and the existing Quality-Eval V1 capture/replay shape.

## 5. Coordinator decisions Don owes

Before any skeleton PR lands:

1. **Browser engine:** Playwright (subprocess) vs WebView2 IPC vs CDP-direct. Recommendation: Playwright. Mature, cross-platform, headless-safe, well-debugged automation surface. WebView2 would couple us to Windows; CDP-direct re-implements what Playwright already does well.
2. **File capability scope model:** explicit allowlist (directories Don grants) vs glob-pattern whitelist vs per-action approval. Recommendation: explicit allowlist + per-action escalation for outside-scope writes. Matches existing `MediaPermissions` shape.
3. **Power User preset implementation:** does it land as part of T1.3 (since T1.3 needs richer presets than today's 3) or as a follow-up? Recommendation: as part of T1.3 — Phase 4 is where Power User becomes meaningful.
4. **Credentials:** explicitly out-of-scope for T1.3. The proposal says "no credential persistence." Confirm? OS keychain integration is a separate later slice.
5. **Skeleton-PR shape:** one combined PR with both `l5-browser/` and `l5-files/` skeletons, or two separate PRs? Recommendation: two separate, one per crate, so each gets its own coordinator review.

## 6. What this proposal does NOT include

- The Playwright dependency itself (skeleton PR adds it conditionally; full impl PRs use it).
- L4 router escalation logic for "this task needs a stronger model to plan a multi-step browser workflow." That's roadmap item 4-6 (model router maturity) — separate.
- Mobile equivalents. Per ADR-0016 §6 the policy_grants rows sync, but the actual mobile capability execution is out-of-scope until mobile ships.
