# T2.1 — Mobile Companion Sync Schema (Design Draft)

> **Why now.** Pro Phase 4 (browser + file workflow tools, T1.3) is about to commit the action-approval framework and audit-replay surfaces to a single-device shape. Sync decisions made *after* P4 lands cost a multi-layer migration. Made *before* P4 lands, they cost an extra column or two in tables that are already being designed. This doc locks the architecture so P4's wiring is sync-aware from the first commit.
>
> **What this is not.** This is not a commitment to ship mobile. It is the schema that any mobile or second-device surface — phone, tablet, web companion, watch, second laptop — would need. If Don decides mobile never ships, the only cost incurred is a few additive columns on already-mutable tables and a handful of `Option<DeviceId>` fields on events. If mobile ships in 18 months, the desktop is already wire-compatible.
>
> **Doctrine grounding.**
> - §6 (single product) — mobile is a *surface* of Companion, not a separate product. No mobile-only release. The desktop and mobile are the same Companion presented in two windows.
> - §4 (UX is top-priority constraint) — continuity across devices is a UX problem before it is a sync-engine problem. The user's relationship with the Companion does not fork at the device boundary.
> - §8 (self-test before review) — the synthetic event-stream validator under `tools/sync-schema-validator/` is the self-test gate for the conflict-resolution rules below.

## 1. Topology

```
+-------------------------+         +-------------------------+
|  Desktop (Tauri / Rust) |         |  Mobile (TBD: Tauri     |
|  — primary writer       | <-----> |  Mobile or RN-over-Rust)|
|  — owns aether.db       |         |  — replica writer       |
|  — owns aether_audit.db |         |  — owns mobile_local.db |
|  — local L1–L7          |         |  — owns mobile_audit.db |
+-------------------------+         +-------------------------+
            ^                                  ^
            |   sync transport (per §6)        |
            +----------------------------------+
```

### 1.1 The two-master assumption

Mobile is **not** a thin terminal. The user opens the app on a phone with no laptop nearby and expects to:
- Have a conversation (turn-taking, voice, presence, persona).
- Save a memory.
- Approve / deny an action.
- See history.

That means mobile must **write** locally. Both devices are masters; sync reconciles their writes. Read-only mobile was rejected:
- It fails the offline test (no laptop nearby = degraded experience that violates §4).
- It re-creates the WhatsApp Web problem (a "real" client and a "shadow" client; users hate it).
- It pushes every action through a network round-trip, undermining L1's timing contracts.

### 1.2 Desktop remains the **audit master**

Even though mobile writes locally, the **canonical audit chain lives on desktop**. Mobile keeps its own `mobile_audit.db` for offline integrity, but on reconnect it streams its append-only audit records into the desktop chain via a **chain-merge protocol** (§5). The desktop's chain is the legal record. Mobile's chain is a temporary shard that gets folded in.

Rationale: L5 invariants (audit hash chain, HMAC, append-only triggers) require a single chain head per install. Two divergent chains is unrecoverable. One chain with a merge protocol is solvable.

## 2. What syncs and what doesn't

Per-domain decisions. The unit of sync is the **table row** (or event), keyed by globally-unique IDs. `change_id` (ULID) is already the cross-layer correlation key per `event_contracts_master.md` §2.4 — we reuse it. We add `device_id: DeviceId` and `origin_seq: u64` (per-device monotonic) to every syncable record.

| Surface | Syncs? | Direction | Rationale |
|---|---|---|---|
| `memory_items` (Personal/Work/Health/Finance/Creative/System) | **Yes — full bidirectional** | Both ways | The user's relationship with Companion is the product. Memory continuity across devices is the §4 demand. |
| `memory_provenance`, `memory_tags`, `memory_artifact_links` | Yes — follows parent | Both ways | Cascades with `memory_items`. |
| `memory_embeddings_ref` | **No — local only** | n/a | Vector store IDs are device-local (each device runs its own embedding index against its own vector store). Re-embed on receive. See §3.3. |
| `memory_tombstones` | **Yes — full bidirectional** | Both ways | Forget on phone must propagate to laptop, *especially* for sensitive items. Tombstones are CRDT-friendly (set union with timestamp). |
| `policy_grants` (active grants) | **Yes — bidirectional with last-writer-wins per `grant_id`** | Both ways | A grant approved on phone applies to the persona, not the device. Revoke on phone revokes on laptop. |
| `policy_audit_log` | **Yes — append-only chain merge (§5)** | Mobile → Desktop primary; Desktop → Mobile for visibility | Mobile writes its local chain; merges into desktop's canonical chain on reconnect. |
| `policy_audit_checkpoints` | Desktop authoritative | Desktop → Mobile (read) | Mobile verifies against desktop checkpoint after merge. |
| `cost_counters` | **Sum-then-reconcile (CRDT-style PN-Counter)** | Bidirectional | Both devices burn API budget; counters must combine, not overwrite. See §4.4. |
| `persona_profiles` (installed persona registry) | **Yes — bidirectional** | Both ways | Active persona must match across devices (per ADR-0012 + ADR-0001 user-keyed memory). |
| `compiled_persona_artifacts` | **No — recompile locally** | n/a | Compiled blobs are device-specific (per-tier). Each device compiles from its own pack files. |
| Persona pack files (Tier-2 download per ADR-0012) | **No — each device downloads independently** | n/a | Pack signature verifies against bundled pubkey on each device. Re-downloading on second device is cheap (~15 MB) and avoids cross-device pack-file shipping. |
| `interaction_sessions` | **Yes — append-only, device-local first** | Both ways (eventually) | History continuity. A turn started on laptop and continued on phone should appear as one session — but cross-device session stitching is **deferred** (§9 OQ-2). For v1, sessions are device-local; sync is for *history visibility*, not *active session migration*. |
| `routing_decisions` | Yes — append-only, device-tagged | Both ways | Cost forensics + audit completeness. Each row is keyed by `(decision_id, device_id)`. |
| `byok_credentials_meta` | **No — device-local** | n/a | Each device has its own OS keyring. The `key_ref` is opaque to the other device. User adds the same provider key on each device independently. The *fact* that a credential exists may sync (provider + fingerprint), but the `key_ref` does not. |
| `approval_requests` (open tickets) | **Yes — bidirectional with deadline-bound TTL** | Both ways | Ask on phone, approve on laptop is a real use case (e.g. high-risk capability the user wants to think about on the bigger screen). See §4.3. |
| `degraded_mode_events` | Yes — append-only, device-local first | Both ways | Each device has its own degraded modes (network, GPU pressure). Sync is for visibility, not coordination. |
| `schema_versions` | **No — device-local** | n/a | Each device runs its own migrations against its own SQLite file. Sync requires schema-version compatibility (§6). |
| Active L1 turn state (in-flight turn) | **No — never synced** | n/a | Turns are device-local. The phone does not "take over" a turn from the laptop mid-utterance. See §4.6. |
| Live media streams (TTS audio, viseme ticks, partial transcripts) | **No — never synced** | n/a | Bus-projected media events stop at the device boundary. Each device runs its own L3 renderer with its own viseme stream. |
| Bus events with `source_layer = Media` | **No — never crossed** | n/a | Per `event_contracts_master.md` §3.8: media events are device-local by construction. |

### 2.1 Summary — what crosses the wire

Three categories:

1. **Durable user state** (memory, persona registry, grants, tombstones) — bidirectional, conflict-resolved per §4.
2. **Append-only audit + history** (audit log, routing decisions, interaction sessions, degraded events) — append-only, chain-merged per §5.
3. **Counters** (cost) — CRDT-merged per §4.4.

Everything else is device-local.

## 3. Sync schema additions

These are **additive** to the existing `sqlite_schema_pack.md` DDL. No breaking changes. Every column has a sane default, so existing rows on a single-device install remain valid.

### 3.1 Common columns added to every syncable mutable table

```sql
-- Added to: memory_items, memory_tombstones, policy_grants, persona_profiles,
--           cost_counters, approval_requests
ALTER TABLE <table> ADD COLUMN device_id        TEXT NOT NULL DEFAULT 'desktop-bootstrap';
ALTER TABLE <table> ADD COLUMN origin_seq       INTEGER NOT NULL DEFAULT 0;   -- per-device monotonic
ALTER TABLE <table> ADD COLUMN logical_clock    INTEGER NOT NULL DEFAULT 0;   -- Lamport
ALTER TABLE <table> ADD COLUMN last_modified_at TEXT NOT NULL DEFAULT '1970-01-01T00:00:00Z';
ALTER TABLE <table> ADD COLUMN tombstoned       INTEGER NOT NULL DEFAULT 0;   -- where not already present
```

Rationale:
- `device_id` — disambiguates concurrent writes; used in §4 conflict rules.
- `origin_seq` — per-device monotonic, enables drop detection on the sync transport (mirrors `event_contracts_master.md` §2.5).
- `logical_clock` — Lamport clock; advances as `max(local, received) + 1` on every write. Used as tiebreak in last-writer-wins.
- `last_modified_at` — wall-clock for human-readable conflict reporting; **not** load-bearing for resolution (clocks lie across devices).
- `tombstoned` — soft-delete flag; required for sync (deletes must replicate as marked rows, not as missing rows).

### 3.2 New tables (sync metadata)

```sql
-- DRAFT (additive; lives in aether.db)

CREATE TABLE sync_devices (
    device_id      TEXT PRIMARY KEY,         -- ULID, generated on first run per device
    device_kind    TEXT NOT NULL,            -- 'desktop' | 'mobile' | 'tablet' | 'web' | ...
    display_name   TEXT NOT NULL,            -- user-facing
    paired_at      TEXT NOT NULL,
    last_seen_at   TEXT,
    pubkey         BLOB NOT NULL,            -- Ed25519; for transport auth
    revoked_at     TEXT
);

CREATE TABLE sync_state (
    peer_device_id      TEXT PRIMARY KEY,
    last_pulled_seq     INTEGER NOT NULL DEFAULT 0,   -- their origin_seq we've ingested up to
    last_pushed_seq     INTEGER NOT NULL DEFAULT 0,   -- our origin_seq they've ingested up to
    last_sync_at        TEXT,
    audit_chain_head    BLOB,                          -- their audit head we've verified to
    FOREIGN KEY (peer_device_id) REFERENCES sync_devices(device_id) ON DELETE CASCADE
);

CREATE TABLE sync_outbox (
    -- Per-table rows ready to ship. Populated by triggers on syncable tables.
    outbox_id      INTEGER PRIMARY KEY AUTOINCREMENT,
    table_name     TEXT NOT NULL,
    row_pk         TEXT NOT NULL,
    op_kind        TEXT NOT NULL,            -- 'upsert' | 'tombstone'
    origin_seq     INTEGER NOT NULL,
    enqueued_at    TEXT NOT NULL,
    delivered_to   TEXT                      -- JSON array of peer device_ids that have ack'd
);

CREATE INDEX idx_sync_outbox_undelivered ON sync_outbox(enqueued_at)
    WHERE delivered_to IS NULL;
```

### 3.3 Embedding re-derivation on receive

When a `memory_items` row is received from a peer:
1. Insert / update the row in local `memory_items`.
2. **Do NOT** copy `memory_embeddings_ref`.
3. Enqueue the row for local re-embedding through the device's own embeddings worker.
4. The `memory_embeddings_ref` row is created locally when the worker completes; it is never synced.

This avoids the vector-store-vendor lock-in problem (`sqlite_schema_pack.md` §11 OQ-1) — each device picks its own vector backend and runs its own model. Embedding cost is the price of cross-device reach.

### 3.4 Audit chain — separate physical DBs

Mobile keeps `mobile_audit.db` with the same shape as `aether_audit.db`. On every reconnect:
1. Mobile streams its `policy_audit_log` rows to desktop in order.
2. Desktop verifies HMAC under the *mobile* HMAC key (pre-shared per §6.2).
3. Desktop appends each verified row to its canonical chain with a wrapping record (`payload.kind = "mobile_audit_merge"`, references mobile's `audit_id` + chain hash).
4. Desktop returns a checkpoint for mobile to fast-forward against.
5. Mobile's local chain remains as a forensic shard but is no longer the authoritative record for the merged window.

Detail in §5.

## 4. Conflict resolution — per-domain rules, not one global policy

A single global policy (last-writer-wins; or CRDT everywhere) is wrong because the domains have different semantics. Memory is set-union with edit semantics; grants are revoke-precedence; counters are sum; audit is append-only. Use the right tool per domain.

### 4.1 `memory_items` — last-writer-wins by Lamport clock, with tombstone precedence

Two devices edit the same memory item:
1. Compare `tombstoned`: if either side is tombstoned, **tombstone wins** (delete is sticky).
2. Compare `logical_clock`: higher wins.
3. Tiebreak: lexicographic `device_id`.

Rationale:
- "Forget this" must never be undone by a stale edit.
- Lamport ordering captures causal precedence without requiring synced wall clocks.
- Deterministic tiebreak prevents oscillation.

Edit content (`content_summary`, `content_inline`) is replaced wholesale, not three-way merged. Memory edits are short and infrequent enough that field-level merge is over-engineered.

### 4.2 `policy_grants` — revoke-precedence; LWW for issued

1. If either side has `revoked_at IS NOT NULL`, **revoke wins** (revoke is sticky like tombstone).
2. Otherwise LWW by `logical_clock` on the row.
3. New `grant_id` collisions are impossible (ULID), so concurrent issuance produces two distinct grants and L5 evaluates them per its precedence rules independently.

### 4.3 `approval_requests` — first-response-wins

The user can approve on phone or laptop. Whichever device records `responded_at` first commits the response; the second device sees the row already responded on next sync and dismisses its UI.

Implementation: `approval_requests.responded_at IS NOT NULL` is monotonic — once set, never modified. On conflict between two devices that both responded:
1. Earlier `logical_clock` wins.
2. Tiebreak: lexicographic `device_id`.
3. The losing device emits a `approval_response_superseded` event for L7 to surface a brief toast ("This was approved on Phone 12 seconds ago").

Open question §9 OQ-3 covers the UX of stale prompts on the losing device.

### 4.4 `cost_counters` — PN-counter CRDT

Cost counters are sum-of-spend. Naive LWW would lose budget tracking. Use a positive-negative counter (PN-counter) keyed by `device_id`:

```
cost_counters keyed by (provider_id, window_kind, window_start)
  per_device_contributions: Map<device_id, { tokens: u64, dollars_cents: u64 }>
  total_tokens             := sum(per_device_contributions.tokens)
  total_dollars_cents      := sum(per_device_contributions.dollars_cents)
```

Storage: a sidecar table keyed by `(provider_id, window_kind, window_start, device_id)`. The view `cost_counters` is rebuilt as the sum.

```sql
-- DRAFT
CREATE TABLE cost_counter_contributions (
    provider_id   TEXT NOT NULL,
    window_kind   TEXT NOT NULL,
    window_start  TEXT NOT NULL,
    device_id     TEXT NOT NULL,
    tokens        INTEGER NOT NULL DEFAULT 0,
    cents         INTEGER NOT NULL DEFAULT 0,
    last_updated  TEXT NOT NULL,
    PRIMARY KEY (provider_id, window_kind, window_start, device_id)
);

-- cost_counters becomes a view summing contributions.
```

Cap-checks (`cost_threshold_hit`) read the **summed** total, so a phone burn that exceeds the cap immediately blocks new spend on the laptop on next sync (or earlier if the user sets a lower local cap as a safety margin — §9 OQ-4).

### 4.5 `persona_profiles` (active-persona pointer)

There's a single "active persona" pointer per user (per ADR-0012: only one persona is installed at a time, ignoring previews). Sync rule:
1. On install on either device, record the install with `device_id` + `logical_clock`.
2. On switch, the device that initiated the switch wins by Lamport (this is the most recent user intent).
3. The losing device receives `persona_swap_begin` with `source_device_id`, runs its own L6 swap pipeline against its locally-installed pack files (re-downloading the new pack if not cached).

Open question §9 OQ-5 covers the case where the user starts a switch on phone but the phone goes offline before completing — desktop should not commit the swap until phone reconnects or a timeout fires.

### 4.6 In-flight turns — never sync

Turns are atomic, device-local, never replicated mid-flight. After a turn ends:
- `interaction_sessions` row is finalized on the originating device.
- That row syncs to the peer for history visibility.
- No "continue this turn on the other device" semantic in v1.

Rationale: L1's timing contracts (250 ms / 800 ms / 2000 ms / 4000 ms) cannot tolerate a network round-trip to a peer. Doctrine §4 ranks UX above implementation convenience; cross-device live turn handoff is a future feature, not v1.

### 4.7 Conflict-resolution test matrix (input to validator §10)

The synthetic event-stream validator at `tools/sync-schema-validator/` exercises:

| Scenario | Inputs | Expected outcome |
|---|---|---|
| Concurrent memory edit | A: edit at clock=5; B: edit at clock=5 | Tiebreak: lexicographic device_id wins; loser converges on next pull |
| Edit + tombstone race | A: edit at clock=5; B: tombstone at clock=4 | Tombstone wins despite lower clock |
| Tombstone + tombstone | A and B both tombstone same row | Idempotent; both converge on tombstoned state |
| Concurrent grant revoke | A: revoke at clock=5; B: edit (extend TTL) at clock=6 | Revoke wins despite lower clock |
| Approval double-response | A: allow at clock=5; B: deny at clock=5 | Lexicographic device_id wins; loser sees superseded |
| Cost counter merge | A: $1.00; B: $2.50 | Total = $3.50 (sum, not max) |
| Cap-cross by sum | Cap = $3.00; A: $1.50; B: $1.80 | Cap hit on next sync (sum = $3.30 > 3.00) |
| Persona swap race | A: switch to Marcus; B: switch to Sara, both at clock=5 | Lexicographic device_id wins; loser hot-swaps to winner's persona |
| Late-arriving audit row | Mobile pushes audit row dated yesterday after laptop has 6 hours of audit since | Mobile row appended at chain head with `wall_time != monotonic_position` flag for forensic visibility; chain HMAC remains valid |
| Schema-version skew | Desktop migrated to v7; mobile at v6 | Mobile rejects sync with `SchemaVersionMismatch`; user must update mobile app |

The validator exercises each of these on a fixture event stream and asserts the convergence outcome.

## 5. Audit chain merge

L5's audit chain is the project's legal record. It cannot fork. The merge protocol:

### 5.1 Local chain on each device

Mobile has `mobile_audit.db` with the same `policy_audit_log` shape, **but the HMAC key is mobile-specific** (derived from a mobile-local OS-keyring entry, paired with desktop at device-pairing time). Mobile writes locally with that key.

### 5.2 Pre-share at pairing

When a new device pairs with desktop:
1. User scans a QR code (or enters a numeric pairing code) on desktop.
2. Devices exchange Ed25519 pubkeys + an HMAC-key seed via a Diffie-Hellman handshake gated by the pairing code.
3. Mobile's HMAC key and desktop's HMAC key are both stored on desktop. Mobile only stores its own.
4. A `device_paired` audit row is appended to desktop's chain.

### 5.3 Push protocol (mobile → desktop)

```
1. Mobile opens transport (§6).
2. Mobile sends its current chain head + last-pushed audit_id.
3. Desktop responds with last-merged audit_id.
4. Mobile streams audit rows from (last-merged + 1) to current head, in chain order.
5. For each row:
   a. Desktop verifies HMAC under mobile's pre-shared key.
   b. Desktop wraps the verified row in a desktop-side audit record:
        kind: "mobile_audit_merge"
        wrapped_audit_id: <mobile's audit_id>
        wrapped_record: <canonical bytes>
        source_device_id: <mobile's device_id>
        prev_hash: <desktop's prior chain head>
   c. Desktop appends the wrapping record to its chain with desktop's HMAC.
6. Desktop returns its new chain head + checkpoint.
7. Mobile fast-forwards its sync_state.audit_chain_head.
```

### 5.4 Conflict-free by construction

Merge order is deterministic per device (each mobile shard appears in the desktop chain in mobile's own chain order). The desktop chain remains append-only. The wrapping record makes mobile-origin rows distinguishable for forensics.

### 5.5 Failure modes

- **Mobile HMAC key compromised.** User revokes the device on desktop (`sync_devices.revoked_at`). New audit pushes from the revoked key are rejected. Already-merged rows remain in the chain (they were valid at the time of write).
- **Mobile chain corrupt (gap or hash mismatch).** Desktop refuses the merge, returns `MobileAuditChainBroken { last_good_audit_id }`. Mobile enters degraded mode (`policy_fail_closed_local`); no new mobile-originated side-effects until the user runs a "factory-reset mobile audit" flow that's audit-logged on desktop.
- **Desktop offline indefinitely.** Mobile keeps writing to its local chain. Mobile reaches a configurable buffer limit (e.g. 10 MB or 30 days, whichever first) and emits a `pending_audit_buffer_full` UI banner. Beyond that, mobile enters degraded mode.

## 6. Transport and identity

### 6.1 Transport — peer-to-peer first, relay-fallback

**Primary:** local-network LAN sync (mDNS discovery, then a long-lived WebSocket-over-TLS to the desktop's listener). Latency ~10ms, no third-party servers, works on the home network.

**Secondary (deferred to §9 OQ-6):** an end-to-end-encrypted relay (e.g. a Cloudflare-Workers-hosted message queue) for sync when the devices aren't on the same network. Encryption keys derived from the pairing handshake; the relay sees only ciphertext + routing metadata.

No "Companion cloud." The desktop is the source of truth; the relay is dumb pipe.

### 6.2 Identity — Ed25519 keypair per device, HMAC key per device for audit

Per §5.2, devices exchange:
- Ed25519 pubkeys (transport auth + signing of sync envelopes).
- HMAC-key seeds (mobile's per-device audit HMAC key, stored only on the device + on desktop).

Pairing requires user-present consent on both devices (QR code + numeric confirmation). No silent pairing.

### 6.3 Sync envelope

```
SyncEnvelope {
  protocol_version: u16,
  schema_version:   u16,        // §6.4
  source_device_id: DeviceId,
  payload_kind:     "memory_items" | "policy_grants" | "audit_chain" | "cost_contributions" | "approval_requests" | "persona_profiles" | ...,
  payload:          <kind-specific batch>,
  signature:        Ed25519Signature,   // over (payload_kind || payload || timestamp)
  timestamp:        MonotonicTimestamp,
}
```

### 6.4 Schema version compatibility

`schema_version` in the envelope must match between devices for sync to proceed. Mismatch:
- Lower-version device refuses incoming envelopes from higher-version peer.
- Higher-version device sends an envelope of `kind: "version_handshake"` only.
- User sees a "Update Companion on your phone to sync" prompt.

This is identical to the event-bus version-handshake rule (`event_contracts_master.md` §5.8).

## 7. Identity / persona continuity

This is where ADR-0001 (memory is user-keyed, not persona-keyed) and ADR-0012 (one active persona on disk) constrain the design.

### 7.1 The active persona is one pointer, synced

```
active_persona_pointer {
  persona_id: PersonaId,
  version:    SemVer,
  switched_at: MonotonicTimestamp,
  switched_by_device_id: DeviceId,
  logical_clock: u64,
}
```

Stored in a singleton table `active_persona_state` (one row, ever). LWW per §4.5 with the Lamport clock as ordering authority.

### 7.2 Each device installs the pack independently

Per ADR-0012, persona pack files are not synced. The active-persona pointer changes; each device fetches the pack from the manifest URL on first activation. ~15 MB cost on the second device.

### 7.3 Compiled artifacts are device-local

Per ADR-0012 + tier-aware compilation: each device compiles the persona for its own hardware tier. Sharing compiled artifacts would couple devices to the same tier and break ADR-0006's tier model.

### 7.4 Memory is user-keyed (ADR-0001 holds)

The user's `memory.db` is a single corpus across devices. Every sensitive item, every fact, every artifact replicates per §2 + §4 rules. Switching personas does not partition memory; switching devices does not partition memory. The user's relationship state is whole.

### 7.5 Voice / face / motion library — device-local

Each device renders presence locally per ADR-0013. Motion clip libraries are downloaded per persona per device. Lip-sync runs locally. None of this crosses the wire.

## 8. Memory domain reach (ADR-0001 dependency check)

T1.1 has an open `MemoryDomain` reconciliation question (per `parallel_software_tracks.md`). This design assumes the **six-domain taxonomy from ADR-0001** is final: Personal / Work / Health / Finance / Creative / System.

All six domains sync bidirectionally per §2 and §4. Rationale:

- **Personal / Work / Creative** — obviously the user's life; cross-device continuity is the entire point.
- **Health / Finance** — the most sensitive domains. The user *especially* wants their health and finance memories on whichever device is at hand. Encryption-at-rest covers the threat model; not-syncing makes the product worse.
- **System** — Companion's own self-state (preferences, settings derived from interaction). Trivially syncs.

**If T1.1 reconciles to a different domain set, this doc updates §2 + §8 only.** The sync schema columns (§3.1) are domain-agnostic; the rules don't change shape, only enumeration.

## 9. Open questions (deferred to Don's call)

1. **OQ-1 — Mobile shipping commitment.** Does Companion mobile ship in v1, in v2, or is this purely defensive design? **Recommendation:** defensive design with full schema reservation. Costs nothing to leave columns nullable; costs months to retrofit.

2. **OQ-2 — Cross-device live session migration.** Should a user mid-conversation on the laptop be able to "continue on the phone"? **Recommendation:** explicitly out of scope for v1. Sessions are device-local; sync is for history visibility. Add as a v2 feature if user research demands it.

3. **OQ-3 — Stale-prompt UX on losing device.** When approval-on-phone wins over approval-on-laptop, the laptop UI was showing a modal that's now stale. Toast + auto-dismiss? Hard close? Show "Approved on Phone 12 sec ago"? **Recommendation:** soft toast + auto-dismiss after 5 sec. Don to confirm.

4. **OQ-4 — Per-device cost cap as safety margin.** Should the user be able to set a *local* cost cap below the *global* cap, to prevent a phone-while-offline burn? **Recommendation:** yes — add `cost_caps_local` per device. Defer implementation to a follow-up.

5. **OQ-5 — Persona swap mid-air.** User starts switch on phone, phone goes offline before completing. Does desktop commit the swap (it's user intent), or wait? **Recommendation:** wait for confirmation — abandoned-swap timeout = 5 minutes, after which desktop emits `persona_swap_rollback` and the user has to retry on whichever device they're on.

6. **OQ-6 — Off-LAN relay.** Do we ship the e2e-encrypted relay in v1, or LAN-only? **Recommendation:** LAN-only for v1. Most "phone with no laptop" cases are at home or work where LAN is fine. Relay is a v2 feature behind a `companion.dbhavery.dev` worker.

7. **OQ-7 — Device-pairing UX.** QR code on desktop scanned by phone? Numeric code typed both ways? Push notification from desktop to phone? **Recommendation:** QR code displayed on desktop, scanned by phone camera. Phone shows confirmation code, user reads it on desktop, both confirm. Audit row on both devices.

8. **OQ-8 — Audit shard pruning.** Mobile's `mobile_audit.db` keeps growing as a forensic shard even after merge. When is it safe to prune mobile-side? **Recommendation:** after desktop confirms `audit_chain_head` includes mobile's last row + a 30-day cooldown. Defer to a follow-up.

9. **OQ-9 — Schema migration order across devices.** When desktop migrates first, mobile is locked out until it updates. What if mobile is the device the user has? **Recommendation:** never auto-migrate desktop on a release that breaks wire compatibility with the still-supported mobile version. Add a "compatible mobile version" field to release metadata.

10. **OQ-10 — Replacing this doc with an ADR.** This file is the design draft. ADR-0016 is the lockable subset. Don accepts ADR-0016 once he's read both. Open questions remain in this doc; the ADR captures what's locked.

## 10. Validation — synthetic event-stream test scaffold

`tools/sync-schema-validator/` is a pure-Python scaffold (no GPU, no new packages). It implements the conflict-resolution rules in §4 against the test matrix in §4.7 and asserts convergence.

Run:
```
python tools/sync-schema-validator/validate.py
```

Output: pass/fail per scenario row, with the input event stream and the resolved state.

Importance:
- Catches mistakes in the conflict rules before they ship.
- Becomes the regression harness for any future change to a rule (e.g. if §4.3 first-response-wins ever turns out to be wrong UX).
- Self-test gate per doctrine §8 — any change to this design must run it green before reaching Don.
