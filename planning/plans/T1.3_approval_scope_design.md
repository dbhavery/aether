## 0. TL;DR

Add a new **`ApprovalScope`** enum that travels alongside `ApprovalMode` on `PolicyDecisionEvent` (and its persisted echo on `policy_grants` rows). It captures the *temporal extent* a user-issued approval covers — orthogonal to *what* was approved (`ApprovalMode`) and *how long* a grant nominally lives (`GrantDuration`).

| Concept | Existing | New |
|---|---|---|
| What is approved (per-action shape) | `ApprovalMode` | unchanged |
| How long a grant lives (calendar-ish) | `GrantDuration` | unchanged |
| Temporal extent of *user approval reuse* | implicit (per-action by default) | **`ApprovalScope`** |

`ApprovalScope` has four variants — `PerAction`, `OncePerSession`, `OncePerTask`, `DraftOnly` — and is **additive**: every existing call site defaults to `PerAction`, every existing serialized event re-deserializes cleanly with the new field absent (`#[serde(default)]`).

The four ways a user can satisfy an `Ask` (`UserChoice` in `approval.rs`) already encode three of these scopes (`Allow`, `AllowSession`, `AllowTask`, `DeferToDraft`). This design lifts that information out of `UserChoice` (which is consumed and dropped) into a **persistent, audit-visible discriminator** on the resulting decision and grant.

---

## 1. Goals and non-goals

### Goals

1. Let users grant approval once per session or once per task and have subsequent same-shape actions auto-approved without re-prompting.
2. Let users (or system policy) elect "Draft only" — the agent prepares the action artifact but L5 does **not** dispatch the executor; the artifact is surfaced in the UI for the user to manually run.
3. Make the chosen scope a **first-class audit field** so the user, the trust center, and red-team replay all see "this auto-approval was granted under scope X at time T."
4. Stay backward-compatible — any caller that ignores the new field gets today's `PerAction` behavior.

### Non-goals (deferred)

- Credential-bearing scopes (e.g. "approve while keychain is unlocked"). Out of T1.3 entirely (parent §5.4).
- Time-windowed scopes ("for 1 hour"). `GrantDuration::Persistent { ttl }` already covers calendar-style TTL; user-facing time-window UI is a follow-up.
- Scope inheritance from parent grants (e.g. a `OncePerTask` grant on `Files.Edit` implicitly auto-approves child `Files.Read` calls). Defer.
- Cross-device sync of session-scoped grants. Sessions are device-local per ADR-0016 §"What does NOT sync."

## 2. The `ApprovalScope` enum

```rust
// packages/l5-policy/src/approval.rs (new type, near UserChoice)

/// Temporal extent over which a user-issued approval applies to subsequent
/// matching actions. Orthogonal to `ApprovalMode` (what is approved) and
/// `GrantDuration` (calendar-style TTL).
///
/// **Default: `PerAction`.** Every existing call site that does not set this
/// field deserializes / constructs as `PerAction` and so behaves exactly as
/// before this enum landed.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
pub enum ApprovalScope {
    /// Today's default. Every action prompts; no reuse across actions.
    PerAction,
    /// User granted for the lifetime of the current session. Resets on app
    /// restart or explicit session end. Device-local (ADR-0016).
    OncePerSession,
    /// User granted for the lifetime of the current task. Task boundary is
    /// defined in §4 below.
    OncePerTask,
    /// Agent prepares the action artifact; L5 does not dispatch the executor.
    /// User reviews and clicks to run — re-entering the policy engine as a
    /// fresh request. Distinct from `Decision::DraftOnly` (which is the
    /// system-side Decision) — `ApprovalScope::DraftOnly` is the *user-chosen*
    /// counterpart, mirroring `DraftSource::UserChoice`.
    DraftOnly,
}

impl Default for ApprovalScope {
    fn default() -> Self {
        ApprovalScope::PerAction
    }
}
```

### Mapping to existing `UserChoice`

`UserChoice` (in `approval.rs`) already enumerates user picks. The mapping below is the canonical conversion:

| `UserChoice` | Resulting `ApprovalScope` | Resulting `Decision` |
|---|---|---|
| `Allow` | `PerAction` | `Decision::Allow` |
| `AllowScope(...)` | `PerAction` (with narrowed `ResourceScope`) | `Decision::Allow` |
| `AllowSession` | `OncePerSession` | `Decision::Allow` + grant issued |
| `AllowTask` | `OncePerTask` | `Decision::Allow` + grant issued |
| `Deny` | n/a (no grant) | `Decision::Deny` |
| `DeferToDraft` | `DraftOnly` | `Decision::DraftOnly { source: UserChoice }` |

`ApprovalScope` does NOT replace `UserChoice` — it is the **persisted, audit-visible** projection of the user's choice that survives past the in-memory ticket.

### Relationship to `ApprovalMode`

`ApprovalMode` already contains a `TaskScoped` and a `DraftOnly` variant. These describe **policy defaults** (what the persona / preset said the approval shape *should* be), not user-chosen scope reuse. `ApprovalScope` describes what *actually happened* on a specific decision. They co-travel: a `ApprovalMode::Ask` capability whose resulting decision was approved with `UserChoice::AllowSession` ends up with `effective_mode = Ask` and `approval_scope = OncePerSession` on the same `PolicyDecisionEvent`.

## 3. Where the field lives

### 3.1 Event surface (`packages/l5-policy/src/events.rs`)

Add an additive field to `PolicyDecisionEvent`:

```rust
pub struct PolicyDecisionEvent {
    // ... existing fields unchanged ...
    pub effective_mode: Option<ApprovalMode>,

    /// Scope under which this decision was approved. `None` on legacy /
    /// pre-T1.3 events (deserializes via `serde(default)` to `None`).
    /// Writers post-T1.3 always set `Some(_)` — `Some(PerAction)` for
    /// today's behavior, `Some(OncePerSession)` etc. for the new modes.
    #[serde(default)]
    pub approval_scope: Option<ApprovalScope>,
}
```

Same additive treatment on `GrantIssuedEvent` so the audit consumer can correlate the issued grant to the scope that birthed it.

### 3.2 Persisted grant row (`packages/l5-policy/src/grants.rs` + storage migration)

Add a nullable column on the `policy_grants` table (DDL lives in `packages/storage/migrations/` per CLAUDE.md §6):

```sql
-- migration: 00NN_policy_grants_approval_scope.sql
ALTER TABLE policy_grants ADD COLUMN approval_scope TEXT NULL;
-- NULL = legacy (pre-T1.3) grant, semantically equivalent to 'PerAction'.
-- Non-null values: 'PerAction' | 'OncePerSession' | 'OncePerTask' | 'DraftOnly'.
```

The Rust `Grant` struct gains:

```rust
pub struct Grant {
    // ... existing fields ...
    /// Scope chosen at issuance. `None` on rows written by pre-T1.3 code.
    #[serde(default)]
    pub approval_scope: Option<ApprovalScope>,
}
```

Read-side: when `covers(...)` matches a grant whose `approval_scope` is `Some(OncePerSession | OncePerTask)`, the engine reuses it without prompting (state machine in §4). When it is `None` or `Some(PerAction)`, today's per-action prompting holds.

### 3.3 Audit row (`packages/l5-policy/src/audit.rs`)

`AuditRecordEvent` already carries `decision: DecisionKind`, `reason: Option<StaticReasonId>`, and (in v2) `original_utterance`/`retrieval_provenance`. Add:

```rust
pub struct AuditRecordEvent {
    // ... existing ...

    /// Scope chosen on the user-facing approval that produced this row.
    /// `None` for: pre-T1.3 rows, system-emitted decisions that never
    /// went to the user (`Decision::Allow` from a pre-existing grant,
    /// `Decision::Deny` from policy without prompting).
    #[serde(default)]
    pub approval_scope: Option<ApprovalScope>,

    /// Backref to the grant that auto-approved this row. `Some(_)` only
    /// when this row was a follow-on use of a `OncePerSession` /
    /// `OncePerTask` grant (i.e. the user was *not* prompted).
    #[serde(default)]
    pub auto_approved_under_grant: Option<GrantId>,
}
```

This pair lets the trust-center UI render: "you approved [capability] for the session at 09:42; below are the 14 actions auto-approved under that grant."

Bumping the audit `schema_version` is **not** required — both fields are `#[serde(default)]`. The audit UI's existing v1/v2 badge logic stays unchanged. (If a future ADR mandates a v3 bump for ABI clarity, do it then.)

## 4. State machine

### 4.1 Task boundary definition

A "task" in this design is a **turn-window**: from the moment L1 emits a `TurnRequest` until the same `TurnRequest`'s terminal `TurnResponse` (success, error, or user cancel) is observed on the bus, plus any sub-turn fan-out the agent issued under the same `change_id` lineage.

Concretely, a `OncePerTask` grant carries a `TaskId` that is the `change_id` of the originating turn. The grant matches a candidate action when:

1. The candidate's `change_id` lineage (or its parent chain) contains the grant's `TaskId`.
2. `(capability, resource, persona)` falls within the grant's pattern under the existing `GrantLedger::covers` rule.

When the turn terminates, the grant is revoked with `RevokeReason::TtlExpired` (re-using the existing reason — semantically "task-end" is a TTL-shaped trigger from the engine's POV). A future ADR may introduce a dedicated `RevokeReason::TaskEnded` for cleaner audit copy; not required now.

### 4.2 Lookup and consumption — recommend "consume-while-scope-valid"

When a fresh `ActionRequest` arrives, the engine asks `GrantLedger::covers(...)` as today. The new behavior:

1. If `covers` returns `Some(grant_id)` and the grant's `approval_scope` is `Some(OncePerSession)`, AND the current session id matches the grant's session id → **auto-approve, write audit row stamped with `auto_approved_under_grant = Some(grant_id)`, do NOT decrement any counter**.
2. If `covers` returns `Some(grant_id)` and the grant's `approval_scope` is `Some(OncePerTask)`, AND the candidate's `change_id` is in the grant's task lineage → same as above.
3. If `covers` returns `None`, or the scope check fails, fall through to normal evaluation (which may emit `Ask`).

**Why "consume-while-valid" not "consume-once-per-N":**

- Matches the user's mental model of the UI string "remember for this session." The user does not expect a counter.
- Eliminates a class of denial-of-service surprises where N is hit mid-task.
- The 8 re-evaluation triggers (DECISION_LOCK_PASS_2026-04-18 Decision 4) already gate misuse: any provenance change, persona swap, cost threshold, posture narrow, etc. forces re-evaluation regardless of the grant.

The grant remains valid until its `expires_at` (TTL), the session ends (for `OncePerSession`), the task ends (for `OncePerTask`), or any of the 8 re-eval triggers fires. There is no use-count cap.

### 4.3 `DraftOnly` is not a grant

`ApprovalScope::DraftOnly` does NOT issue a grant. The semantics:

1. L5 evaluates the request, decides that a draft is the right output (either system-initiated → `DraftSource::System`, or user picked `DeferToDraft` → `DraftSource::UserChoice`).
2. L5 emits `Decision::DraftOnly { source, audit_id, reason }`. The audit row carries `approval_scope = Some(DraftOnly)`.
3. The execution layer **does not** dispatch the side-effect executor. The agent surfaces the prepared artifact (file diff, planned navigation, planned form fill) to L7.
4. When the user clicks "run it," L7 emits a **fresh** `ActionRequest` with a new `request_id` that re-enters L5. The previous `Decision::DraftOnly` row stays as the historical record; the new request is evaluated independently. There is no "promotion" path inside L5.

This keeps `DraftOnly` audit-clean and prevents a class of bugs where a draft-then-execute looks like a single decision.

## 5. UI implications (wire-string contract)

The approval modal in L7 (the UI is React, but L5 ships only the wire strings) gains the following surface. **This doc specifies the contract; the React lives in T2.4-equivalent UI work.**

### 5.1 Modal radio shape

Single radio group with four options. Display order is fixed:

| Wire id | Default label | Affordance state |
|---|---|---|
| `allow_once` | "Allow once" | Default selection. |
| `allow_task` | "Allow for this task" | Available when the request carries a task lineage. |
| `allow_session` | "Allow for this session" | Always available (for `Ask` capabilities). |
| `defer_draft` | "Draft only — let me run it" | Available when the capability has side effects. |

Plus a separate **Deny** button. Deny is not in the radio group (it is the safety-default escape, not a scope choice).

### 5.2 "Remember for [scope]" copy

The radio labels above already encode the scope; there is no separate "remember for…" checkbox. (An earlier draft proposed a checkbox; the radio shape collapses it into the choice itself, which matches the underlying `UserChoice` enum 1:1 and prevents the "remember unchecked + AllowSession" contradiction.)

### 5.3 Wire payload — `ApprovalResponse`

The L7 → Rust `ApprovalResponse` (`approval.rs:35`) does not change shape. The `user_choice: UserChoice` field already carries the scope. The radio id maps to `UserChoice` via:

| Radio id | `UserChoice` |
|---|---|
| `allow_once` | `Allow` (or `AllowScope` if the modal lets the user narrow the resource) |
| `allow_task` | `AllowTask` |
| `allow_session` | `AllowSession` |
| `defer_draft` | `DeferToDraft` |
| (Deny button) | `Deny` |

### 5.4 Re-prompt suppression

When a `OncePerSession` / `OncePerTask` grant auto-approves a follow-on action, L7 receives no `ApprovalPending` event for it. L7 may show a passive "auto-approved under [grant]" toast (UX choice; out of L5 scope). L5's contract ends at "no `ApprovalPending` is emitted; the `PolicyDecisionEvent` carries `approval_scope` and `effective_mode` so L7 can render history correctly."

## 6. Audit-row implications (event shape)

### 6.1 Two row types under a non-`PerAction` grant

A user choosing `AllowSession` produces **two** audit rows over time:

1. **The granting row** — written when the user clicks "Allow for this session." Fields:
   - `decision = DecisionKind::Allow`
   - `approval_scope = Some(OncePerSession)`
   - `auto_approved_under_grant = None` (this IS the granting decision)
   - co-emitted with `GrantIssuedEvent`

2. **N follow-on rows** — written for every subsequent matching action that the engine auto-approved under the grant:
   - `decision = DecisionKind::Allow`
   - `approval_scope = Some(OncePerSession)` (echoed for filterability)
   - `auto_approved_under_grant = Some(grant_id)` ← the discriminator
   - **no** `ApprovalPending` event was ever emitted for these

### 6.2 Filter + summary support

`AuditFilter` (`audit.rs:213`) gains an additive optional filter:

```rust
pub struct AuditFilter {
    // ... existing ...
    /// Limit to rows that were auto-approved under a grant of this scope.
    pub approval_scope: Option<ApprovalScope>,
}
```

`AuditSummary.by_decision` does not need a new key — `DecisionKind::Allow` covers the auto-approved follow-ons. The trust-center UI computes the breakdown by joining on `auto_approved_under_grant`.

### 6.3 `DraftOnly` rows

Already covered by `DecisionKind::DraftOnlyUserChoice` and `DecisionKind::DraftOnlySystem`. The new `approval_scope` field on the row redundantly stamps `Some(DraftOnly)` for `DraftOnlyUserChoice` rows so a single column filter can find every "draft-only" outcome regardless of source. For `DraftOnlySystem` rows, `approval_scope` stays `None` (the user did not choose the scope; the system did).

## 7. Sync implications (per ADR-0016)

`policy_grants` syncs **bidirectionally with revoke-precedence; otherwise LWW by Lamport** (ADR-0016 row table line 41). The new `approval_scope` column does not change that rule — it is just another LWW column.

### Per-scope sync recommendation

| `ApprovalScope` | Sync? | Rationale |
|---|---|---|
| `PerAction` | n/a (no grant row) | No grant persisted. |
| `OncePerSession` | **device-local; do NOT sync** | Sessions are device-local per ADR-0016 §"What does NOT sync" / OQ-2. A session grant on Don's desktop is meaningless on his phone — the phone has its own session. |
| `OncePerTask` | sync (LWW) | Tasks are turn-windows that can fan out across devices in the future (out of v1 scope, but the row should sync so audit history is consistent). The task lineage (`change_id`) is global; the grant is portable. In practice on a single device this is a no-op. |
| `DraftOnly` | n/a (no grant row) | DraftOnly is a per-decision shape, not a grant. |

**Implementation hook:** the sync layer's grant filter (which today is "is this row eligible for outbound replication?") gains a check: `approval_scope == Some(OncePerSession)` → skip outbound. Inbound `OncePerSession` rows from another device are dropped on read with a single audit log line ("ignored device-local scope from peer"). This keeps the LWW machinery honest while honoring ADR-0016.

No change to ADR-0016 itself — this nuance is documented here and in the T1.3 implementation PR's commit body.

## 8. Backward compatibility checklist

- [x] `PolicyDecisionEvent.approval_scope` is `#[serde(default)] Option<ApprovalScope>` → old wire payloads deserialize cleanly.
- [x] `Grant.approval_scope` is `#[serde(default)] Option<ApprovalScope>` → old persisted grants load cleanly with `None`.
- [x] `policy_grants.approval_scope` SQL column is `NULL`-able with no default → existing rows untouched.
- [x] `AuditRecordEvent.approval_scope` and `.auto_approved_under_grant` are both `#[serde(default)]` → audit chain HMAC computation skips defaulted absent fields per existing canonicalization rule (writer emits `Some(_)` post-T1.3; readers tolerate either).
- [x] No change to `ApprovalMode` (`Auto | TaskScoped | Ask | DraftOnly | Deny`). The existing variants remain semantically valid; `ApprovalScope` adds an orthogonal axis.
- [x] No change to `Decision` variants — just a new field on the *event* form.
- [x] `UserChoice` unchanged. The mapping to `ApprovalScope` is engine-internal.
- [x] No change to ADR-0016 sync rules.
- [x] CI lint additive: a single new `cargo-deny` allow for the new enum's serde traits (none expected; `derive(Serialize, Deserialize)` is already permitted on the workspace).

Every existing call site that constructs `PolicyDecisionEvent` / `Grant` / `AuditRecordEvent` via struct literal must add `..Default::default()` or set the new field explicitly. The implementation PR audits these sites; this design assumes there are ≤30 such call sites across `packages/l5-policy/` and the legacy `policy_engine.rs` shim.

## 9. Out-of-scope (deferred)

Per the prompt, explicitly deferred:

1. **Credential-bearing scopes** — e.g. "approve while keychain unlocked." Needs OS-keychain integration which parent §5.4 already deferred to a later slice with its own threat-model review.
2. **Time-windowed scopes** ("for 1 hour"). `GrantDuration::Persistent { ttl }` is the engine-side primitive; the UI layer can choose to surface a duration picker in a follow-up. No L5 change needed at that point, only L7.
3. **Scope inheritance from parent grants.** Example: a `OncePerTask` grant on `Files.Edit` implicitly auto-approves child `Files.Read` calls in the same task. This intersects the capability hierarchy + the 8-trigger re-eval rule in non-trivial ways. Defer to a dedicated mini-ADR after T1.3 ships and we have telemetry on how often the absence bites users.

## 10. Open questions for Don

1. **Task boundary for fan-out actions.** §4.1 says a `OncePerTask` grant matches when the candidate's `change_id` *lineage* contains the grant's `TaskId`. This means deeply-nested sub-tasks inherit the grant. Acceptable, or should the grant terminate at the first sub-task boundary? Recommended: lineage-inclusive (matches the user's mental model of "this whole task").
2. **`OncePerSession` outbound sync.** §7 recommends device-local. Confirm? Alternative is sync-but-tag-with-device-id, but that adds replay-ambiguity for no clear UX win.
3. **`auto_approved_under_grant` as audit field — fold into `stage_trace` or first-class column?** This design picks first-class column (faster filter, clearer schema). `stage_trace` is already a `Vec<StageTrace>` of strings, which is the "diagnostic" lane, not the "stable schema" lane.
4. **Default fix-up of legacy `Grant` rows.** When the v1 → v2 audit migration happens (post-ADR-0009), should we backfill `approval_scope = Some(PerAction)` on legacy grants, or leave them `NULL`? Recommended: leave `NULL` and treat `NULL == PerAction` at read time. Backfill costs migration time for zero behavior change.
